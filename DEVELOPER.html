01

1. What the application is

fetchconfig-web is a single-file Perl CGI/FastCGI application (fetchconfig-web.cgi) that provides a browser UI in front of the command-line tool fetchconfig (a network-device configuration backup engine). It lets operators browse per-device backups, view/compare/download configurations, trigger on-demand backups, edit the fetchconfig device table, manage users and site-based access, and read audit and status information.

It is deliberately one file. All Perl logic, the HTML generation, and the client-side JavaScript live in fetchconfig-web.cgi. The stylesheet was externalised in 2.00 to fetchconfig-web.css (served statically, cacheable). Static assets (CSS, fonts, images, help/documentation HTML) live under a web-served directory; see section 9.

Source-of-truth boundaries (important mental model)

DataOwner / source of truthfetchconfig-web's role
Device table (flat file)fetchconfig CLI + the web editorreads/parses on demand; writes via the editor
Device backups (files on disk)fetchconfig CLIreads only (view/compare/download)
Users, sites, audit, sessions metadataPostgreSQL (this app owns it)full read/write
Configuration/etc/fetchconfig-web.cfgre-read on every request; never written

The web app never owns the device table or the backups -- fetchconfig does. Treat the flat file and the backup tree as external inputs.

2. Runtime model: CGI and FastCGI

The script runs under either plain CGI or FastCGI (mod_fcgid). A global $RUN_MODE records which. Under FastCGI the process is long-lived and serves many requests in a loop, so per-request state must be reset between requests or data leaks from one user's request into the next.

The request loop

  • The last lines of the file are the entry point. Under FastCGI an FCGI::Request accept loop calls handle_request(CGI->new) once per accepted request; under plain CGI a single handle_request(CGI->new) runs and the process exits.
  • handle_request($q) owns one request. It assigns $cgi = $q, calls reset_request_state() (on an error string it shows the misconfiguration via show_login_form() and returns), ensures $SESSION_DIR exists, then calls main().
  • reset_request_state() runs at the start of every request. It clears the request-scoped globals (the warning flags $SECURITY_WARNING / $AUDIT_WARNING / $EXTERNAL_CHANGE_NOTICE, the memoization caches $_sites_cache, %_user_sites_cache, $_allowed_dirs_cache, $_templates_t_cache, $_template_used_cache, $_fatal_error_cache, plus _syntax_cache_reset()), then re-reads the config file and returns read_config()'s error string, if any. It does not clear $cgi -- handle_request() assigns that fresh per request. If you add a request-scoped cache or global, you MUST clear it here.
  • One cache is deliberately not cleared here: $_templates_t_persist, the cross-request cache of fetchconfig.pl -t (see run_templates_t). -t forks a full engine process; persisting its result across FastCGI requests avoids that fork on every editor load. It is validated on use by a cheap device-table stat signature (_templates_t_sig) plus a TEMPLATES_T_TTL (60s) ceiling, and cleared outright by _invalidate_table_caches() after a save. Under plain CGI the process is per-request, so it is always undef and the behaviour is identical to re-forking every time.
  • main() is the dispatcher: it reads action, enforces the POST-only guard, resolves the session, runs the CSRF and site-scope guards, then runs the if/elsif dispatch chain.

Why the driver sits at the very end of the file

Several large data tables (%COMMON_OPTS, %MODEL_CATALOG, %EMAIL_OPTS, $SECRET_KEEP, the base64 logo/icon blobs) are built with run-time my assignments scattered through the file. The handle_request(CGI->new) calls are on the last lines so all of those have executed before main() dispatches anything. Do not move the driver earlier.

3. File / code layout (sections)

The .cgi is organised top-to-bottom into labelled sections:

  1. Module imports -- use strict; use warnings; then the use list (CGI, CGI::Cookie, DBI, MIME::Base64, File::Path, Algorithm::Diff, etc.; FCGI and Crypt::Bcrypt are optional and loaded defensively). DBD::Pg is never used -- DBI loads it implicitly from the dbi:Pg DSN -- and Digest::SHA is required lazily at its two call sites (_reset_token_hash, _sha256_file).
  2. Constants -- all use constant (version, min-fetchconfig, login-throttle windows, reset-token TTL, bcrypt cost, audit page size, the masking banner).
  3. Config-file handling -- @CFG_KEYS registry, parse_config_file, read_config, validators.
  4. CGI / FastCGI request core -- request-scoped globals, reset_request_state, handle_request, main (the driver is at EOF, per section 2).
  5. Functions -- everything else (auth, DB access, rendering, editors, tools), each with a uniform 80-# header block.

Every sub carries a header of the form:

perl 
################################################################################
# name
#
# <description>
#
# Parameters:
#   $arg1   ...
################################################################################
sub name { ... }

Match this format when adding functions.

4. Request lifecycle (the dispatch path)

code 
browser request
   -> handle_request(CGI->new)     (EOF: FCGI accept loop or one-shot)
      -> $cgi = $q
      -> reset_request_state()     (clear per-request globals/caches, then
                                    re-read the config; fatal banner if broken)
      -> ensure $SESSION_DIR exists
      -> main()
          1. $action = $cgi->param('action') || '' (sanitised)
          2. POST-only guard for %STATE_CHANGING actions -> 405
          3. pre-auth actions (login, logout, forgot/reset) branch out here
          4. current_session()  -> ($sid, $username, $csrf, $pw_warn) or ()
          5. unauthenticated?  -> show_login_form(...) with the "next" deep link
          6. CSRF check for state-changing actions (see section 7.4)
          7. per-device site-scope guard
          8. dispatch:  if ($action eq 'X') { handler($user) } elsif ...

The same flow as a diagram:

flowchart TD
    A([Browser request]) --> B["EOF driver: handle_request(CGI->new)<br/>FCGI accept loop or one-shot"]
    B --> C["reset_request_state()<br/>clear per-request globals + caches;<br/>re-read the config"]
    C --> F{read_config OK?}
    F -- no --> G[["Fatal config banner"]]
    F -- yes --> D["ensure SESSION_DIR; main()"]
    D --> E["parse action; POST-only guard"]
    E --> H["current_session()"]
    H --> I{Authenticated?}
    I -- no --> J[["show_login_form()<br/>carry the next deep link"]]
    I -- yes --> K{State-changing action?}
    K -- yes --> L{CSRF OK?}
    L -- no --> M[["403 / reject"]]
    L -- yes --> N["site-scope guard; dispatch to handler"]
    K -- no --> N
    N --> O[["render: page_head .. page_foot"]]

The dispatch is a long if/elsif chain on $action (~130 actions). Each branch calls a handler sub. Read-only actions (view_report, status, compare, compare_devices, compare_device_versions, rename_device_id (the rename form), ...) render directly. State-changing actions (login, user_save, add_site, note_save, backup_now, rename_device_do, replay_db_change, ...) are in %STATE_CHANGING and are CSRF-protected and POST-guarded.

The Rename device-id feature (2.14+) is a front-end for the engine's fetchconfig.pl --rename-device-id --old=X --new=Y (9.78+): rename_device_id shows the form, rename_device_do runs the engine (mode=preview adds -T; mode=commit performs it, then migrates the web-owned device_notes row and writes an audit entry), and replay_db_change runs --replay-db-change to flush the engine's history-DB outbox. Both run via run_fetchconfig_priv() (the sudo path -- run_fetchconfig and run_fetchconfig_priv now share the run_capture_cmd() core), so the rename can create the device-table lock and move the backup tree as the fetchconfig owner rather than the web user. The edit_table editor shows an existing device's Device-ID read-only (a new, unsaved device's is still editable), because changing it there would desync the backups/history -- use Rename device-id instead. Gated on rename_feature_available() (engine >= RENAME_MIN_FETCHCONFIG_VERSION) and user_may_rename_device() (all-sites editor). The DB side is a privilege-only migration (2.14): UPDATE on dev_id for the writer on backup_runs / backup_versions (column-scoped on PostgreSQL 8.4+, whole-table UPDATE below 8.4 where column-level GRANT is unsupported; the writer owns the tables, so effective access is unchanged). backup_current already had table-wide UPDATE.

The %STATE_CHANGING set

A hash (map { $_ => 1 } qw(...)) listing every action that mutates state. The CSRF gate and POST-only guard consult it. Any new mutating action MUST be added to this set or it will be rejected (or, worse, left unprotected). Tests assert membership (see FCWebTest::state_changing_actions).

5. Configuration subsystem

5.1 The config registry (@CFG_KEYS)

All settings are declared in one array of tuples:

perl 
[ 'KEY_NAME', 'type', 'default-or-(required)', 'human value hint', $min, $max ]
  • type drives validation. The full set is bool, cronuser, enum, file, int, path, path_opt, siteurl, str, str_req, url. (enum_onoff and secret are device-table option types from %COMMON_OPTS -- see section 6 -- not config types.)
  • $min/$max bound integer types.
  • (required) means no default; read_config fails loudly if it is missing.

read_config() parses /etc/fetchconfig-web.cfg (via parse_config_file), validates each value against its registry entry, applies defaults, and assigns the file-scoped my $KEY globals. Validation errors surface as a configuration error on the login page; a bad file does not crash the process.

To add a config key: add one @CFG_KEYS tuple, declare the my $KEY global in the top declaration block, assign it in read_config, and document it in README.md (a test asserts every registry key is documented). Provide a safe default; only use (required) for things with no reasonable default.

5.2 Web paths (2.00+)

WEB_DIR (filesystem root for static assets, presence-checks only), BASE_URL (URL root the browser uses), and the sub-paths CSS_BASE_URL / FONT_BASE_URL / IMAGE_BASE_URL / JS_BASE_URL / HELP_BASE_URL. The stylesheet must exist at <WEB_DIR><CSS_BASE_URL>/fetchconfig-web.css or every page shows a red "directories not configured" banner. HELP_BASE_URL (2.03+, default /help) is the help tree: help.html plus the fetchconfig-web/ and fetchconfig/ sub-directories that help_scan_dir() scans to build the two "additional help" menus (label from each file's <title>, capped at HELP_MAX_FILES).

JS_BASE_URL (2.09+, default /js) holds mermaid.min.js, the self-contained Mermaid renderer bundled in the release's js/ directory. It powers the Template viewer state-machine diagram (show_view_template), which is a server/client split: template_mermaid_source() loads fetchconfig's own fetchconfig::model::GenericTemplateParser by absolute path from FETCHCONFIG_PATH -- eval-guarded and require-idempotent, exactly like fetchconfig_installed_version() loads Constants.pm, and never copied into the app -- then the gloss/mermaid subs ported verbatim from the engine tool gen-template-docs.pl (tdiag_action_gloss / tdiag_trigger_gloss / tdiag_edge_label / tdiag_mm_label / tdiag_target_of / tdiag_mermaid) emit the stateDiagram-v2 source. The browser renders it with <JS_BASE_URL>/mermaid.min.js, pulled in only on that page, using the IBM Plex Sans webfont (FONT_BASE_URL, needed so labels fit) via an inline scoped @font-face -- no shared CSS change, so no cache-bust. The source is HTML-escaped into <pre class="mermaid"> (and tdiag_mm_label strips Mermaid metacharacters), so a template cannot inject markup. Missing parser, missing mermaid.min.js, a missing font, or a template that does not parse each yield a short note rather than a (possibly stale) diagram.

Device-table option entry shape

Each catalog option is { type => '<validator>', mandatory => 0|1 }. type selects an input widget and a validator (secret -> masked field with show toggle, enum_onoff -> on/off, enum_snmp_level -> noAuthNoPriv/authNoPriv/authPriv, path -> allow-listed directory, int, enum_site, debug, ...). The parsed device table and the catalog together drive the editor UI and the save-time validation (cfg_value_problem).

A parsed option value is normally the pair [$key, $value]. A credential field (one in %CRED_FIELD_KIND) may carry a third element, [$key, '$Alias', 'alias'], tagging the value as a pw: alias reference rather than a literal. cred_parse_value sets the tag on read (a defined $Name); cred_serialize_value emits it bare on write, and emits a literal with quote-XOR-leading-escape (first-character-only \$/\\). fold_cred_aliases (gated by ALIAS_REPLACE_ON_SAVE) turns a verbatim value that equals a defined alias's value into the alias on save. See fetchconfig-pw-alias-grammar-engine.md.

7. Security model

Security is layered; the important mechanisms:

7.1 Authentication and password storage

  • Passwords are hashed with bcrypt (Crypt::Bcrypt, cost BCRYPT_COST=12); bcrypt_available() probes the build at runtime (AIX-safe). With REQUIRE_BCRYPT=1 (default, 2.10+) password_hash() never falls back to the legacy Apache MD5 ($apr1$) -- it dies instead -- and do_login() refuses to log anyone in (with a login-screen notice) when the module is unavailable, so a broken crypto stack fails closed rather than silently weakening hashes. verify_password() still reads legacy $apr1$ hashes so they can upgrade to bcrypt on the owner's next login. Set REQUIRE_BCRYPT=0 to re-enable the fallback on a stack without Crypt::Bcrypt.
  • The per-password salt comes from secure_random_bytes() which reads /dev/urandom, loops on short reads, and dies rather than falling back to rand() (fail-closed). Session IDs and reset tokens use the same source.
  • A constant-time path guards login against user-enumeration timing: a nonexistent user is still compared against a cached dummy hash (dummy_password_hash, memoised in a closure).

7.2 Sessions

  • Server-side, file-based. A session file lives at $SESSION_DIR/$sid where $sid is 48 hex chars (24 random bytes). $SESSION_DIR is created 0700.
  • File format: five lines -- username, expiry (epoch), csrf token, pw_warn flag, login_time (epoch). The 5th line is fixed for the life of the session and drives the SESSION_MAX_LIFETIME cap; the idle slide rewrites lines 1-4 but preserves it. Legacy four-line files (written before the cap) are still accepted and get a login_time on first load. load_session validates the sid shape before touching disk.
  • Two expiries: idle SESSION_TTL (slides) and absolute SESSION_MAX_LIFETIME (hard cap from login). Password change/reset invalidates sessions.
  • Cookie: HttpOnly; SameSite=Lax; Secure is added (and HSTS emitted) when effective_https() is true. That is HTTPS_ENABLED (default 1, 2.10+) OR a TLS request detected from the server env (HTTPS=on / REQUEST_SCHEME=https) OR, only when TRUST_FORWARDED_PROTO=1, a reverse proxy's X-Forwarded-Proto. An HTTP-only deployment must set HTTPS_ENABLED=0 or the Secure cookie is never returned over plain HTTP and login cannot complete.

7.3 CSRF protection

  • Each session has a CSRF token (csrf_token()); forms emit it via csrf_field() (a hidden csrf input).
  • csrf_ok() checks the submitted token for every state-changing action. Login and logout are handled specially (login has no session yet).

7.4 Request hardening

  • State-changing actions are POST-only and CSRF-checked (the %STATE_CHANGING set).
  • Login/reset throttling: login_attempts (keyed by IP and by username) with a failure window (LOGIN_WINDOW_SECS) and cooldown (LOGIN_COOLDOWN_SECS); LOGIN_MAX_FAILURES trips the throttle. Designed to avoid both a timing oracle and FastCGI-worker exhaustion.
  • Password policy: length bounds and per-class minimums (PASSWORD_MIN_*, PASSWORD_MIN_CLASSES); a new password must differ from the default and from the username.
  • HSTS header when HTTPS; Cache-Control: no-store on dynamic pages.

7.5 Authorization (roles + site scoping)

  • Rights are per-user boolean columns: edit_device_table, admin_function, download_full_report, download_full_config, read_debug (the last must be granted explicitly -- unlike the others it is not implied by being site-unrestricted, since a debug log can hold a cleartext device password). PROTECTED_USER is the built-in super-admin that cannot be deleted or de-admined.
  • Site scoping: a device's site= tag restricts which users see it. A site-limited user only sees/edits devices tagged with their assigned sites (user_sites). Enforcement is centralised in read_device_ids() / user_site_access().

7.6 Config view masking

  • The config view is always masked (mask_secrets); an unmasked copy is gated behind the per-user download_full_config right and is audited.
  • mask_secrets redacts secrets in config text: Cisco secret|password <type> <hash> (universal), SNMP community, RADIUS/TACACS keys, WPA passphrases, Aruba CX controller/auth-server keys, bare indented key lines, etc. Masking runs before syntax highlighting, so the highlighter never sees cleartext.
  • A pw: credential alias ($Name) is a name, not a secret: mask_secrets, mask_secrets_opt and audit_redact leave a bare $Name visible in a credential slot, while a verbatim secret value is still masked/redacted. The pw: block itself is server-only (re-emitted from disk, pw: pass values masked by mask_pw_pass).
  • valid_report_name / template_path_ok / the directory allow-lists (read_allowed_dirs) prevent path traversal for report/template/file access.

7.7 Privilege separation

  • "Backup Now" and every template-directory mutation can run via sudo (USE_SUDO_FOR_BACKUP_NOW, TEMPLATE_HELPER) so the web user itself needs no write access to the repository/templates. The sudo command is built in one place per operation with fixed arguments.
  • The template helper fetchconfig-web-install-template.pl (v1.7) is the single privileged helper, run through sudo. Its subcommands:
  • Templates (.tmpl): install (save, keeps one .bak), install-new (atomic create-if-absent, used by template upload and by the HEX generator's final install), revert, delete (template + .bak), and rename (atomic, refuse-if-exists, moves the .bak). Each is wrapped by a CGI function (save_template, install_new_template, delete_template_file, rename_template_file) that falls back to a direct filesystem op when no helper is configured and the directory is web-writable.
  • Debug logs (.debug, v1.5): read-debug <file> [offset] [length] and delete-debug <file> -- fetchconfig writes these as root, mode 0600, so the viewer/delete go through the helper (debug_log_window, do_delete_debug).
  • Schedule (v1.6): list-cron <user> -- a read-only crontab -l for CRON_USER, used by cron_list_raw for Tools -> Show schedule, because the cron spool directory is root-owned. The user is validated and must exist (getpwnam); nothing is ever written. v1.7 forces LC_ALL=C (so cron_list_raw's "no crontab" match works on a non-English Linux host) and resolves crontab by absolute path under a sane PATH. Helper-failure output is condensed to one line by helper_fail_msg / helper_error_summary (so an out-of-date helper's --help dump is never shown), with a redeploy hint when a subcommand is unrecognised. A new subcommand needs no sudoers change -- the grant is on the script path -- only a redeploy.
  • The HEX uploader runs <FETCHCONFIG_PATH>/tools/generate_template.pl directly (not via sudo) with -f <hex> -o <out>, reads the draft template from the -o file, stamps syntax_style, then installs it through the helper like any upload. The input is validated first (hex_looks_like_record_session, 1 MB cap).
  • SQL is always parameterized (DBI placeholders). The one place a column name is interpolated (db_set_user_flag) uses a fixed allow-list.

7.8 Audit logging

  • audit(%args) appends a row to audit_log for every security-relevant event (login success/failure/throttle, user/site/permission changes, config view, external device-table change, errors, ...).
  • Secret field values are redacted via %AUDIT_SECRET_KEY.
  • An external-change tripwire detects when the device table was modified outside the app (compares a stored token; records owner + mtime) and warns on the next page / editor open.
  • Audit-write failure raises an operational (amber) warning rather than silently losing the event.

7.9 Subprocess resource limits

  • Every subprocess capture (run_fetchconfig, run_command_capture, run_privileged) reads stdout+stderr concurrently via IO::Select/select to avoid the classic open3 pipe-fill deadlock, and bounds the captured bytes by CAPTURE_MAX_BYTES (default 50 MiB; 0 disables). On overflow the child is killed and reaped: the parsed paths (run_fetchconfig, run_privileged) discard and return a controlled error, while run_command_capture (the Backup Now transcript) keeps the partial output and reports the error, exactly as it does on a BACKUP_TIMEOUT.

7.10 Dependencies and scanning

  • Runtime deps are pinned in cpanfile / Makefile.PL; install them into the CGI's own Perl with cpanm --installdeps . (or the distro packages listed in INSTALL). Crypt::Bcrypt is required by default (REQUIRE_BCRYPT=1).
  • The archive does not pin OS/package versions, so scan the deployed stack for known advisories: the installed Perl modules (e.g. OSV-Scanner against the cpanfile, or cpan-outdated), and the OS packages for Perl, the web server and PostgreSQL. Treat a clean scan of the deployed versions -- not the source -- as the release gate.

8. Database (PostgreSQL)

The app owns a PostgreSQL schema created by fetchconfig-web-dbsetup.pl. Upgrades ship as fetchconfig-web-dbupdate-<ver>.sql. All access is via DBI with a fresh connection per request (no pooling); every query is parameterized.

8.1 Tables

DEVICE_TABLE is not a database table. It is fetchconfig's own on-disk text config file (the device_table), owned and written by the fetchconfig engine -- fetchconfig-web only reads it. It appears in the diagrams solely to anchor the dev_id / device_id / site values the database tables carry; every link to it is logical (dashed), never a database foreign key.

The tables form three independent groups -- the schema-version ledger, the web UI tables, and the Backup Dashboard history tables -- documented in that order. In the ER diagrams solid lines are real foreign keys and dashed lines are logical links enforced in code. (Mermaid lays sibling entities out horizontally, so each group is its own narrower diagram.)

Schema-version ledger

A single standalone table with no relationship to any other table (not to the web UI tables, not to the backup history). The --upgrade tool reads and writes it to decide which dbupdate scripts to apply.

8.2 Connection and grants

db_connect() opens a DBI handle (RaiseError=0, AutoCommit=1) and returns undef on failure (callers show a "server misconfiguration" message rather than leaking details). The setup script grants the web user the minimal privileges (no DELETE on app_state, etc.). There is no ORM; queries are inline DBI.

8.3 Schema changes

9. Static assets, rendering, and the UI

  • HTML is generated in Perl (print qq{...}), not templated. page_head() emits the <head> (linking the external stylesheet with a ?v=<APP_VERSION_INTERNAL> cache-buster -- the true shipped version, so new CSS is always picked up; never the config-overridable APP_VERSION), the title bar, the menu, and any warning banners; page_foot() closes the page.
  • CSS is the external fetchconfig-web.css (served from WEB_DIR). The only inline CSS left in the CGI is the app-wide @font-face block (see below), the dynamic login backdrop (depends on login state), the Template viewer's scoped diagram styles, and style="display:none" toggle targets for JS; email HTML uses inline styles by necessity.
  • Design tokens: a :root block at the top of the CSS is the single source for shared values -- use a token, never re-hardcode one of these:
  • fonts: --font-ui, --font-mono, --font-head (== --font-ui until a branded heading face is adopted);
  • semantic colours, each with a strong value and a light tint (background + border): --color-accent / -accent-dark / -accent-bg / -accent-border; --color-danger / -danger-dark / -danger-bg / -danger-border / -danger-text; --color-success / -success-bg / -success-border; the warning trio --color-warn / -warn-bg / -warn-border; and --color-focus (every form-control focus ring);
  • neutral greys: text dark to light --color-ink, --color-heading, --color-label, --color-muted, --color-faint, plus --color-border (the one hairline border / divider grey);
  • --diff-add / --diff-del / --diff-hunk -- the unified-diff palette on the dark config surface, shared by the config-view diff (pre.config .d-*) and the report diff (pre.diff.rep-diff) so the two cannot drift.

The inline styles page_head() emits (login backdrop, the diagram note box, the bcrypt warning) reference these tokens too. (The dashboard keeps its own --dash-* status palette in a second :root; the report "state" badges are a deliberate distinct-hue set and .state-new keeps its own teal. Not tokenised: the light surface-fill greys -- table-header/hover backgrounds such as #eaecef, #f6f6f6, #dfe3e8 -- the mint section border #cdeede, and the dark debug-log palette.)

  • Webfonts: IBM Plex Sans (UI) and IBM Plex Mono (config/diff/log views), Regular + SemiBold, ship in fonts/ (both SIL OFL 1.1) and load app-wide via an @font-face block page_head() emits inline -- inline because the src URL needs the configured BASE_URL/FONT_BASE_URL, which the static stylesheet cannot interpolate (and the B8 audit forbids a $placeholder in the CSS). Both --font-* tokens list the Plex family ahead of the platform stack and use font-display: swap, so an uninstalled file degrades gracefully to the system font. The Template viewer additionally carries its own scoped copy of the Sans faces so the diagram survives changes to page_head.
  • Sections/boxes: content panels use .tool-section (green) or .tool-section-blue; the title bar is .tool-section-title. Long pages get a floating Top/Bottom nav (top_bottom_nav()).
  • Syntax highlighting of configs is done by per-scheme highlight_* functions, selected by highlight_config() after masking.
  • Debug log rendering (highlight_debug_log(), debug_log_transcript()) is registered in %SYNTAX_HIGHLIGHTERS under the pseudo-model __debug__, the same way the template viewer uses __template__. It is not in template_syntax_schemes(), so it is never user-selectable. Three things about it are load-bearing and easy to break:
  • The hex field is positional, not tokenised. A Net::Telnet dump_log line is <dir> 0x%05x: followed by exactly 16*3 + 4 characters of hex (DEBUG_HEX_WIDTH) and then the ASCII gutter. _dbg_hex_line() measures that field relative to the end of the offset match, never from a fixed column, because the offset widens past 1 MB. Both the hex view and the transcript go through that one function; keep it that way.
  • Each line's newline goes INSIDE its <span>. The Sent-only / Received-only filter is CSS display:none on whole lines; with the newline outside the span, a filtered view would be a column of blank rows. t/D1-debug-viewer.t asserts \n(?!</span>) never matches.
  • user_may_read_debug deliberately breaks the sibling pattern. The other per-user right accessors open with return 1 if user_is_unrestricted($dbh, $username), and user_is_unrestricted means "not limited to any site", NOT "admin". That would hand debug logs -- and so device passwords -- to every non-admin account with no site restriction. It is admin OR the explicit flag, never implied. Do not align it with the others.
  • The size bands are enforced in three places and must agree: show_debug_log refuses over DEBUG_MAX_BYTES, do_download_debug re-checks the same ceiling server-side (the greyed button is only UI), and debug_log_read splits anything over DEBUG_VIEW_FULL_MAX into two DEBUG_VIEW_CHUNK pieces. The cut marker is composed between two independently highlighted chunks, never parsed out of the content, and carries only dbg-cut so no filter can hide it.
  • Real .debug files are CRLF. fetchconfig's ssh client writes its stderr through a pty, and ONLCR rewrites every \n. Each renderer strips a trailing \r per line. Leave it in and it lands inside the gutter span, where it sits before a tag rather than before the emitted \n -- the HTML parser then treats it as a line break of its own, every hex line renders as two, and hiding the span hides the text but not the second line. That is what made the direction filter look like it only greyed lines out.
  • Net::Telnet writes a blank line after every dump block. It carries no direction, so it must be tagged with the block it closes (dbg-blank plus that block's direction class) or it survives the filter -- one blank row per hidden block, which on a device that trickles its output is most of the page. It must also stay transparent to turn detection, since in a real log every hex line is preceded by one.
  • ssh chatter is classified by COMPLEMENT. A .debug file holds only fetchconfig's five # markers, dump_log hex lines, and the ssh client's stderr (master_stderr_fh => $debug_fh in Abstract.pm). input_log is never attached, so device bytes reach the file only as hex lines. Hence dbg-ssh = not a hex line and not a # marker, which makes pre.config.no-ssh .dbg-ssh { display: none } provably unable to hide session data. Do not "improve" this into a list of ssh message prefixes -- that would be version-, log-level- and locale-dependent, and it would turn a guarantee into a guess. The # markers are deliberately outside the class so # [secret sent - not logged] can never be hidden by a toggle.
  • The gutter is Latin-1, not UTF-8. dump_log prints bytes 0x80-0xFF literally, so _dbg_esc() widens them to UTF-8 (via _cp_utf8()) to match the app's raw-bytes-out + charset=UTF-8 model. Plain esc() would put invalid UTF-8 on the page.

The SEND/RECV labels are CSS ::before content, not markup: generated content is not part of textContent, so the shared copy button still returns the file byte for byte with its original < / > glyphs. Do not "simplify" this by writing the labels into the HTML.

  • Static downloads from WEB_DIR: recorder_download_html() renders the session-recorder download row (record_session.exe / .py) only for files actually present in WEB_DIR, linking them at BASE_URL/<name> (served by the web server, not the CGI). Their SHA-256 is computed by file_sha256_cached() and memoised in <SESSION_DIR>/.recorder-sha256, keyed by mtime+size.

12. Conventions and gotchas

  • Reset request state: any new request-scoped global/cache must be cleared in reset_request_state() (FastCGI leak risk).
  • Escape all output: use esc() (HTML-escape) on every interpolated value; never emit user/DB data raw.
  • Parameterize all SQL; never interpolate a value, and interpolate a column name only from a fixed allow-list.
  • Fail closed: on RNG/DB/validation failure, deny rather than degrade.
  • Function headers: match the 80-# block format; keep lines <= 80 cols in code where practical (inline HTML print qq{} is exempt).
  • Masking before highlighting: never pass unmasked config to the UI.
  • The driver stays at EOF; do not relocate the handle_request(CGI->new) calls.
  • One file: resist splitting unless you also rework the deployment and test harness -- the single-file property is intentional (simple deploy).

13. The fetchconfig interface (results and token contract)

fetchconfig-web drives the fetchconfig.pl engine as a black box over three channels: the process exit code, its text output (stdout / stderr), and the files it writes (the per-device .status file, the saved-config filenames, and Constants.pm). Everything the web app keys on is catalogued here so the engine side can see what must stay stable.

Any change to a token, record format, status-file key, filename format or exit-code meaning listed below is a breaking change for fetchconfig-web. Each item names its consuming function and whether a break is functional (a feature misbehaves) or cosmetic (display only; a fallback still works).

13.1 Execution pipelines

  • run_fetchconfig(@args) -- open3, stdout and stderr kept separate; returns ($out, $err, $status, $fork_err). Used for every parsed mode (-l, -g, -m, -s, -t, -o, -e, --template-syntax).
  • run_command_capture(@cmd) -- stdout and stderr merged, with keepalive and abort handling; returns ($out, $status, $err, $aborted). Used for the live Backup Now run and the destructive -D scans (the full transcript is the point).
  • run_privileged(@cmd) -- open3, separate, binary-safe; used for the sudo debug-log helper (reads fetchconfig's .debug files), not for fetchconfig.pl itself.

Reliability rules in every pipeline: the exit code is trusted only if waitpid reaped our own PID (guards a stale $? under concurrent scans); EINTR reads are retried, not treated as EOF; total captured output is bounded by CAPTURE_MAX_BYTES (over-limit -> kill child, return an error, discard the truncated buffer).

13.2 Two regimes, and the per-mode evaluation

There is a hard asymmetry worth stating first: the main backup run always exits 0, so its exit code is meaningless -- the .status file is the authoritative success signal and the log text is only a fallback. Every auxiliary mode instead uses the exit code as the primary signal, with text as a cross-check or a benign-exception handler.

13.3 Exact token / format contract

A. Per-device .status file (the authoritative backup result; parsed by read_status_file, read_all_status, and the Backup-Now inline parse). Each field is matched as ^\s<key>\s=\s*<value>:

  • backup_start_date, backup_start_time, backup_end_date, backup_end_time -- value \S+ (displayed).
  • backup_duration_sec -- value \d+ (displayed; also the live-status spinner).
  • backup_state -- value \S+. Logic depends on the exact value failed (-> failure in backup_run_failed); success, unchanged, initial and any other value are treated as success. Functional.
  • backup_changed -- value \S+. Expected unchanged / changed / initial / forced; used only to build the ch-<value> display class, not for logic. Cosmetic.

Renaming any key, or the failed state token, is a functional break (success/failure misdetection and blank last-state display).

B. Saved-config filename format (parse_backup_timestamp, suffix helpers). The basename is expected as <dev_id>.<tag>.YYYYMMDD.HHMMSS<TZ>[.suffix]:

  • timestamp: \.(\d{4})(\d{2})(\d{2})\.(\d{2})(\d{2})(\d{2})([A-Za-z]*) -- the trailing timezone is assumed alphabetic.
  • optional appended suffix: \.\d{8}\.\d{6}[A-Za-z](\.[^.].)$.

Changing the timestamp layout blanks the date/time columns and confuses the suffix tool. Functional (for the dated views), otherwise cosmetic.

C. Exit-code meanings (summarised from 13.2; each is a contract): -l non-zero = "no backups / error"; -g -n -m uses the diff convention (0 / 1 / greater-than-1); -s uses 0 / 1 / 2; -o and -e use 0 / 1 / greater-than-1; -Z uses 1 = "found" (not an error); -t uses 0 / 1 / 2. The full backup run must keep exiting 0 (or, if that ever changes, the web app still relies on .status, not the code). Changing any of these numeric meanings is functional for that feature.

D. Structured stdout record formats:

  • -l -- tab-separated index<TAB>size<TAB>path, newest first; index is digits. Rows not matching ^\d+\t are ignored. (list_backups, device_backup_status.) Functional.
  • -t -- tab-separated ID<TAB>section<TAB>full_path<TAB>model<TAB>dir (at least 5 fields); section must be exactly default or device; the trailing # found ... summary line (^\s#) is skipped. (run_templates_t.) Functional.*
  • -g -- raw config bytes, passed through unmodified (no format dependency).
  • -g -n -m diff text is styled by leading +++ / --- / @@ / *** markers only. Cosmetic.

E. Literal text strings matched in stdout / stderr (case-insensitive):

  • no backed up config files found -- -l: the benign "never backed up" state, distinguished from a real error. (list_backups, device_backup_status.) Functional (rename -> a new device reads as an error, not "no backups yet").
  • there is no latest config -- the benign initial-backup line, excluded from error scraping. (backup_run_failed, fallback path.) Cosmetic/fallback (only matters when no .status was written).
  • \berror: -- generic failure marker scraped from the Backup-Now log, only when .status is unavailable. (backup_run_failed.) Cosmetic/fallback.
  • backup_state\s=\sfailed in free log text -- the same fallback. Fallback.
  • -s text cross-checks, used only if the exit code is missing/unexpected: inconsistent backup suffixes, does not match the backup file suffixes, configured suffix\s+matches the backup file suffixes. (device_suffix_status.) Cosmetic/fallback (exit code is primary).
  • debug:\sregistering model: (with a <prog>: debug: prefix) -- folded into a summary for display. (collapse_model_registration.) Cosmetic.*
  • ^fetchconfig\.pl: -- a stray diagnostic line skipped during --template-syntax scheme parsing. Cosmetic/defensive.

F. Version module (fetchconfig_installed_version; a file read, not a run): FETCHCONFIG_PATH/fetchconfig/Constants.pm, package fetchconfig::Constants, function version() returning a dotted string. Compared against the web app's MIN_FETCHCONFIG_VERSION (currently 9.77) by version_cmp (leading integer of each dotted component). Moving or renaming the module, package or version() yields the "version could not be determined" banner. Functional for the warning (non-fatal to the app).

G. CLI flags / options the web app passes (the invocation contract -- each must keep its name and argument shape): -devices=<file> (always), -l <dev>, -g <dev>, -n <idx>, -m <idx>, -s <dev>, -t, -o, -e, -Z, -D (with a scan flag, destructive), --template-syntax <path>, and the bare run (-devices=<tmp> only) for Backup Now. Removing or renaming any flag breaks the corresponding feature. Functional.

Not a contract (intentionally tolerant): the raw -g config bytes and the config-syntax highlighters render device-vendor content, not fetchconfig output, so they depend on device formats rather than the engine. The main run's exit code is explicitly not relied upon. Anything marked cosmetic above degrades gracefully (a display folds differently, or a fallback keyed on .status / the exit code still decides correctly).

13.4 Backup Dashboard

Optional, ENABLE_DASHBOARD-gated, DB-only. The dashboard reads three history tables the fetchconfig engine (9.75+) writes via its db: option: backup_current (one row/device, Overview + table), backup_runs (one row/run, the trend), backup_versions (one row/saved backup, carries the per-version sha1). fetchconfig-web only reads these (SELECT); the engine writes. The lone exception is the admin cleanup action (below), which deletes via a separate connection as the writer role.

Access. The Overview (show_dashboard_overview; dashboard_overview_allowed = ENABLE_DASHBOARD) is open to every authenticated user: a site-limited user sees only their own sites (tiles, trend and By-site scoped via read_device_ids($user)), an unrestricted user the whole fleet. All devices and Orphan dashboard cleanup are admin-only (dashboard_allowed). After login, users land on the Overview when the dashboard is enabled (do_login).

Orphans. A device-id with history/inventory rows but no device-table entry is an orphan (decommissioned, renamed, or removed outside the app). device_in_table and device_has_db_rows classify one id; dashboard_orphans returns the fleet set. dashboard_devices_rows tags such a row status => 'orphan' (so it is never counted stale), dash_badge renders the red Orphan DB pill, and the row/backups-page action is Orphan dashboard cleanup (action=dashboard_cleanup, renamed from Cleanup dashboard) instead of View/Backup now. do_dashboard_cleanup_delete deletes the backup_ and the three device_inventory tables in one writer transaction (db_table_exists-guarded for older schemas). No new grant: the writer owns the inventory tables, so it may delete their rows -- the "history append-only, no DELETE grant" note in dbsetup is about not granting DELETE to a non-owner, not the owner. Every tile and panel on both pages carries a scope pill -- global (blue) or restricted (red) -- driven by the unrestricted flag the data functions return. dash_scope_pill($scope) renders it (inline next to a panel heading, or pinned top-right inside a tile via dash_tile's optional $scope argument), so a site-limited user can tell at a glance that every number on the page covers only their sites. The scope is per viewer (uniform across a page), not per box.

Config join. site, model and template are config-only (absent from the backup tables), so the device views join backup_current to the parsed device table by dev_id (dashboard_devices_rows, dashboard_overview_data): site code -> description via db_all_sites; generic devices shown as generic · <template>; Site shown as code / description and the client-side filter keyed on the site code. The All-devices table and its CSV (do_dashboard_devices_csv, action dashboard_devices_csv) render the full visible set once and filter/sort/paginate client-side (sort by Last backup (default, newest first) or Status, over the whole set). A device with no backup_current row shows No data, distinct from Never (row, no good backup).

Cleanup (show_dashboard_cleanup / do_dashboard_cleanup_delete, in %STATE_CHANGING): dashboard_orphans lists dev-ids present in the three tables but absent from the device table; the delete is all-or-nothing in one transaction via db_connect_as_writer (credentials from the device-table db: record, so the web login stays SELECT-only), and is audit-logged.

Backups-page SHA1. show_backup_list appends a per-row SHA1 button when backup_sha1_map (keyed on backup_versions.path) has a hash for that backup; sha1_copy_script copies it. Best-effort -- no button when the history schema is absent. It is an integrity checksum, not a cryptographic signature.

  • Timestamps are a naive local wall-clock epoch -- the engine encodes its local time with timegm(local), so the web renders with gmtime (dash_fmt_ts) and computes age against dash_naive_now(). No timezone conversion anywhere. Single box / one TZ makes this correct and simple.
  • State detection (dashboard_schema_state): missing (no table) / nogrant (no SELECT) / empty (no rows) / ok. Non-ok renders dashboard_state_block guidance; the empty panel prints the db: string (writer name from app_state_get($dbh, 'dashboard_writer'), password masked).
  • db_host parse/format is shared (db_host_parse/db_host_format) and mirrors the engine's rule exactly, so the panel emits what the engine parses.
  • Schema install/upgrade lives in fetchconfig-web-dbsetup.pl --upgrade (run as root): ledger schema_migrations, applies pending .sql oldest-first via Perl DBI (no psql), creates the writer role, and grants. --upgrade sets the three history tables' owner to the writer (so it can run the cleanup DELETE), while schema_migrations stays superuser-owned; the web login is SELECT-only. The writer's SELECT grant is also required by the engine's pre-9.5 DML. --upgrade (2.12) additionally grants the web user SELECT on schema_migrations (so the About dialog can report the applied schema version via db_schema_version_cached -- the highest ledger id by version_cmp; without the grant the ledger is invisible to the web role and About reads "not installed"), and grants the writer UPDATE (lines_added, lines_removed) on backup_versions (so --db-backfill can fill them). version_cmp compares per-component integers, so three-part ids (2.12.3) and 2.12 vs 2.9 sort correctly; schema ids are deliberately two-part (one per schema change), distinct from the app's VRM shown as About's Internal version*.
  • The renamed "General parameters" editor tab has admin-only structured db: fields; they round-trip via parse_device_table (kind db), reconstruct_records_from_form (guarded by the db_section marker; db_pass restores from $SECRET_KEEP), and serialize_records. db_pass is masked in display and marked audit-secret.
  • TODO (follow-up): live-DB integration tests for the read layer, the --upgrade runner, the cleanup delete, and the engine's backup_current upsert (the sandbox has no PostgreSQL, so these paths are covered only by unit/stub tests); and the DB-cleanup retention algorithm (keep-count aware, not purely time-based).

13.5 Changes view (config churn)

Dashboard -> Changes (show_dashboard_changes; route dashboard_changes; dashboard_changes_allowed = ENABLE_DASHBOARD, same open/site-scoped model as the Overview). It answers "how often does config actually change", which is independent of backup freshness -- a device backed up nightly but unchanged for years is stable, not stale.

Data source. Everything comes from backup_versions, where one row = one stored config version = one change event in both eras: the engine writes a version file only when the config changed, and the 9.76 --db-backfill pass imports one row per on-disk backup with its real historical file_timestamp. So live and back-filled rows are directly comparable -- no clustering-at-import distortion (that caveat is a backup_runs/trend concern, not this view).

dashboard_changes_data($dbh,$user,%opt) is pure SELECT (unit-tested against a mock handle, t/E10-dashboard-changes.t) and returns: 7d/30d change counts; changed_24h (distinct devices); most_changed (30d leader); stable_1y; a 16-week churn series (weeks, zero-filled; spike = n >= 5 && n >= 3*median of non-zero weeks); top (30d leaderboard, device-table devices only); change-age buckets (<=7d / 8-30 / 31-90 / 91-365 / 1-2y / >2y, plus none = device-table devices with no version yet); and the feed. %opt is feed_n / feed_days (the feed's cap and window; defaults 50 / 7). All scoped to the caller's visible devices (read_device_ids + a dev_id IN (...) clause) for a site-limited user; whole fleet otherwise.

Back-fill (retention) caveat. The weekly chart marks the pre-cut-over region hatched. cutover = MIN(run_end) FROM backup_runs WHERE duration_sec IS NOT NULL (the first live-recorded run; back-filled runs have duration_sec = NULL). Weeks ending at/before it are reconstructed from the backups still on disk -- pruned or expired versions leave no row -- so those counts are a floor and can undercount the deeper past. The caveat is about retention completeness, not timestamp accuracy.

Feed delta (line counts, 2.12). The "Top N recently changed - last D days" feed shows +added / -removed lines straight from backup_versions.lines_added / lines_removed -- written by the fetchconfig engine (9.77+, ignore-aware so volatile lines do not count) on the live save path and by --db-backfill. Pure DB, no file reads. The columns are added by fetchconfig-web-dbupdate-2.12.sql (via dbsetup.pl --upgrade, which also grants the writer UPDATE on them for the backfill). Rendering: a defined pair -> +a / -r (0/0 = only ignored lines changed, shown ±0); NULL -> -- (no stored delta: the device's oldest retained version, which had no on-disk predecessor to diff -- earlier backups may have been pruned -- or a row written before 9.77). It deliberately does not show "new": the web cannot distinguish the oldest retained version from a genuine first-ever backup once earlier versions are pruned, so claiming "new" would be wrong (e.g. apgmg00, whose oldest kept version is NULL but which clearly predates it). N/D come from the n / days query params, validated and clamped (N<=500, D<=365). Each row's View diff links to show_changes_diff (?action=changes_diff&dev=…&ts=<file_timestamp>): it resolves that version's path from the DB, maps it to fetchconfig's own on-disk backup index via list_backups (the index -m/-n expects -- never a DB-derived one, which could drift from the on-disk enumeration), and diffs index N (this version) against N+1 (the previous) through compare_backups. So a device that appears several times in the feed jumps straight to the exact two configs, instead of the device view where the user had to find them. Guarded by device_accessible. The oldest retained version (no earlier backup on disk) shows a note and a device-view link rather than a diff; the diff itself is the full raw fetchconfig.pl -m output (may show more lines than the ignore-aware count). MIN_FETCHCONFIG_VERSION is bumped to 9.77 (a non-blocking header warning when older).

Overview card. show_dashboard_overview adds a compact Recently changed - last 24 h card (dashboard_recent_changed) linking through to this page -- the first thing checked after a maintenance night.
